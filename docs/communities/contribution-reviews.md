# Reviewing a community evaluation

A contributor can propose a missing case, publish a reproduction, or show exactly where a method fails. A good outcome is another builder finishing a real task with fewer corrections. The public challenge provides a cheap first test. Eligibility for a hosted tenant or a paid route is a separate decision.

## Work with the contributor

| Stage | Accountable person | Record that moves the work forward |
| --- | --- | --- |
| Propose | Contributor | A short public excerpt with expected and observed results. A pseudonym used in an exported record does not hide the GitHub account submitting the issue. Raw prompts, private customer artifacts and held-out tasks stay private. |
| Triage | Repository maintainer | Reply on the issue with the workload and reproduction command, a precise request for missing evidence, or a reason to close. Ask before publishing additional material. |
| Reproduce | A builder other than the author | Identify the reviewed source and fixture revisions, runner conditions, prediction or artifact digest, and result. Record founder assistance, corrections and failures. A second execution by the same author can test determinism; it cannot establish independent adoption. |
| Incorporate | Maintainer and reviewer | Accept a specific case or improvement by reviewed PR, link the issue, credit the contributor as requested and name the limitation. A declined or corrected contribution keeps its reasoning accessible. |
| Change a live route | Existing runtime and release owners | Apply the existing protected comparison, tenant grants, budget reservation and release approval. Record canary scope, stop condition and rollback target. A public issue or public challenge score cannot authorize this stage. |

A contributor can ask on the issue to correct their evidence, change attribution, or withdraw a proposal from future consideration. For material that should never have been public, use a private maintainer contact rather than quoting it again. Maintainers can remove references they control. Public copies may persist. The public evaluation handoff confers no model-training grant.

## Run the lab with a founder

**Before the first run**, Frank or the commissioning user chooses one outcome and the smallest improvement worth adopting, plus the maximum cash and human time at risk. The implementation owner freezes the baseline, data revision, rubric and decision rule. One named maintainer owns the disposition. Independent evaluators control unseen cases. Never train or tune on a set that still serves as a release holdout.

**At each review**, show the output and a counterexample next to each other. Present all attempted jobs, including abstentions, timeouts and retries. Show eligible unique cases per cohort, coverage, accepted outputs, cash and replacement cost, review minutes, and time to first useful outcome. Leave missing measurements unknown. Compare only like tasks, revisions and budgets.

**After adoption**, track independent reuse to a buyer-accepted output and the continued performance of that version. Count a distinct builder and accepted task once, link back to the contributing method, and retain correction and withdrawal history. A visit, download, repeated fixture or author self-test cannot count as independent reuse. Customer-success and contribution reports use the same definitions. Do not identify private tenants in public scorecards.

The first operating cycle succeeds when one contributor files a public case, a second builder reproduces or challenges it without founder intervention, and a maintainer returns a reasoned decision. Capture the first failure if the sequence stops. Decide on a recurring paid offer after a customer repeats the workflow and the unsubsidized margin supports the review burden.
